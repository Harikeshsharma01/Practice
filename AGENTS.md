# Sewestian shared website and Android contract

The owner explicitly wants future requests and fixes applied to the website AND Android experience in Harikeshsharma01/Practice. Preserve this requirement across sessions. Work in this existing checkout; do not create another worktree unless requested.

- The Android app is a native WebView client of the same MERN frontend/API, not a separate copy of lessons. Implement learning features, styling and student/teacher workflows in shared client/server code. Do not fork an Android-only syllabus or message database.
- Check desktop, phone-browser and Android WebView implications for every relevant change. Report untested device behavior honestly. Website deployment must reach the server the APK actually uses; separate classroom and hosted databases do not sync automatically.
- Student questions/feedback and teacher replies live on the shared backend. An inbox code links the same student inbox between browsers and APK installations on that server. Classroom approval is still required separately. Do not expose student messages, recovery secrets or teacher credentials publicly.
- The website's `/mobile` page is the app download entry, and `/downloads/Sewestian.apk` serves the verified current APK. `shared/android-release.json` is the release metadata/version source; `scripts/sync-android.mjs` validates and stages the APK for dev/build. Keep the APK, checksum and metadata consistent.
- Shared web changes normally require deploying the frontend/backend and refreshing the app, not rebuilding the native binary. For native Android changes, increment versionCode/version in the shared release metadata, build with `npm run android:apk`, verify signatures/checksum, and distribute the new APK through the same download page. Do not claim an installed binary silently upgrades itself.
- Preserve the private signing key in ignored `.android-private/`; never commit or print its contents. A new signing key cannot update existing installs. Prefer the existing key and disclose any missing-key limitation.
- Run meaningful relevant tests: `npm test`, `npm run build`, `node tests/support-browser.mjs` for inbox/download changes; classroom tests for access changes; Android policy/build/native smoke tests for native changes. Keep APK emulator/physical-device limitations explicit.
- User authorization covers committing and pushing requested changes to the existing Practice repository. Publishing Git commits is not proof that Vercel, Render, MongoDB or the teacher's local computer has deployed them. Report these separately.
